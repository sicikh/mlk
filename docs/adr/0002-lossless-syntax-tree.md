# Use a lossless syntax tree

- Status: accepted
- Date: 2026-09-20

## Context and Problem Statement

`mlkc` is both a batch compiler and a language server.
The two consumers have opposite needs:

- the compiler wants to parse whole files, fast;
- the language server parses incomplete code
  that is syntactically invalid most of the time.

Both consumers need:

- exact source spans for every node and token
  (diagnostics, go-to-definition, rename);
- full fidelity with the source text:
  every whitespace and comment is preserved,
  so that the tree round-trips to the original bytes;
- a tree for _every_ input, however broken.

A traditional parser that builds a typed AST directly cannot provide this:
it discards trivia,
it has no representation for invalid fragments,
and it produces no tree at all when parsing fails.

## Decision Drivers

- Losslessness: the tree must preserve all of the source text.
- Error resilience: parsing must never fail and never panic.
- Performance: access to the children of a node must be cheap and direct.
- One tree for all consumers: the same representation serves the compiler and the LSP.
- Control over the foundation: every other crate depends on the tree,
  so it must be ours to tune.
- Precedent: rust-analyzer and biome have proven this design in production.

## Considered Options

- **Typed AST built directly by the parser** --- the classic compiler design:
  the parser emits AST nodes and drops trivia.
- **Lossless CST on the original rowan** --- the library behind rust-analyzer:
  trivia is stored as separate tokens
  interleaved with the children of a node.
- **Lossless CST on the biome-rowan fork** --- biome's fork:
  trivia is attached to tokens,
  and the children of a node have a static structure.

## Decision Outcome

Chosen option: "Lossless CST on the biome-rowan fork",
because it combines losslessness with a static tree structure,
which the original rowan cannot offer,
and it is both faster and more convenient to work with.

### The tree is lossless

The concrete syntax tree (CST) stores the source text in its entirety:

- every token carries its exact text;
- whitespace and comments (trivia) are stored, never dropped;
- any node can produce the exact source range it covers;
- the tree round-trips to the original file bytes.

This is the foundation for precise diagnostics,
for IDE features that map spans back to the source,
and, later, for a formatter.

### Why the biome-rowan fork and not the original rowan

In the original rowan,
trivia is stored as regular tokens
interleaved with the structural children of a node.
As a result, the shape of a node's children list is dynamic:
retrieving a specific child (say, the `name` of a function declaration)
requires scanning the children
and matching each one by its kind.

The biome-rowan fork stores trivia as part of tokens:
each token owns its leading and trailing trivia pieces.
The children list of a node then contains only structural children,
in an order that is statically known for the node kind.
Field access is generated from the grammar
and resolves in constant time:
there is no scanning by kind.

The static structure has a price:
a raw node constructor could silently build a malformed tree.
Trees are therefore built through a generated `SyntaxFactory`,
which knows the slot structure of every node kind
and attaches trivia to the right tokens.

Notably, rust-analyzer is currently migrating its own syntax
infrastructure to exactly this design,
which validates the choice[^ra-rowan-pr-219].

[^ra-rowan-pr-219]: rowan, _Make trivia first class member of token,_ PR [#219](https://github.com/rust-analyzer/rowan/pull/219).

### The fork is vendored as `mlkc-rowan`

The fork lives in `crates/mlkc-rowan`,
mirroring how biome maintains `biome_rowan`.

Vendoring gives us control over the most foundational crate:

- we can fix bugs and tune performance without waiting for upstream;
- upstream changes land only when we port them deliberately;
- the crate follows the workspace conventions (naming, lints, features).

### Grammar-driven codegen

`SyntaxKind`, the typed node API, and the `SyntaxFactory`
are generated by `xtask codegen`
from a single grammar file, `mlk.ungram`[^ungrammar].
The generated code lands in `mlkc-syntax` and `mlkc-syntax-factory`.
The grammar describes the shape of the tree, not parsing rules:
ambiguities and precedence live in the parser.

[^ungrammar]: Aleksey Kladov, _Introducing Ungrammar,_ <https://rust-analyzer.github.io//blog/2020/10/24/introducing-ungrammar.html>

This is the same split rust-analyzer and biome use:
the grammar is the single source of truth,
and every consumer of the tree is updated by re-running the codegen.

### Error recovery via bogus nodes

The parser never fails.
Panics in the parser are bugs:
a crash on invalid input is unacceptable for a language server.

When the input does not match the expected shape,
the parser:

- skips the unexpected tokens;
- wraps whatever could be salvaged into a _bogus node_
  of the expected category
  (`Bogus`, `BogusDecl`, `BogusExpr`, `BogusPat`, `BogusTy`);
- continues parsing the rest of the file.

Bogus nodes are not part of the language grammar:
they exist only in the green tree.
Their children are untyped syntax elements,
so a bogus node can hold any mix of tokens and nodes.

This keeps the tree well-formed
and marks exactly where recovery happened.
The errors themselves are produced later,
by the diagnostics layer.

### Positive Consequences

- One representation serves the compiler and the language server.
- Every span is exact,
  so diagnostics and IDE features need no span bookkeeping of their own.
- The AST layer is mechanical:
  a grammar change flows through the codegen,
  and the compiler points at every affected call site.
- Invalid input can never crash the tooling;
  fuzzing targets the quality of recovery instead.
- The vendored fork can be profiled and optimized in place.

### Negative Consequences

- Two representations to reason about (CST and the typed AST layer),
  which is more to learn than a plain AST.
- The grammar and codegen are mandatory infrastructure:
  adding a node kind means editing `mlk.ungram` and regenerating.
- The fork must be maintained:
  upstream fixes require manual porting.
- Lossless trees carry the memory cost of the full source text;
  this is mitigated by green tree interning.
