# Make MIR a uniform SSA control-flow graph over words

- Status: accepted
- Date: 2026-10-01

## Context and Problem Statement

[ADR-0005][0005-compiler-pipeline.md] names MIR as the stage after type checking:
"a per-function control-flow graph, typed and layout-resolved",
and leaves two things open:
what MIR is made of,
and whether an A-normal form stage (AIR) sits between the checked HIR and MIR.

The back end is now being designed, so both have to be answered.
The requirements are:

- MIR is a control-flow graph of basic blocks;
- SSA is built on that same MIR with block parameters,
  not in a second set of data structures:
  the CFG form and the SSA form share one representation;
- every value is a `Word` ([ADR-0018][0018-values-as-words.md]),
  so MIR carries no per-value machine types;
- MIR is the level of our own optimizations:
  WASM receives no optimizations from Cranelift,
  and the WASM backend ([ADR-0020][0020-wasm-backend.md])
  ends in the emission of bytes, not in an optimizer of its own,
  so everything worth doing must be expressible here;
- MIR is backend-agnostic:
  WASM is the first consumer, Cranelift the second;
- MIR follows the pass contract of [ADR-0009][0009-pass-contract.md]:
  a pure, total, deterministic function of an assembled input.

The question:
what are the data structures of MIR
such that the CFG form, the SSA form, verification, dumping, and both back ends
all read from them, and a body stays the unit of invalidation
([ADR-0004][0004-module-system.md], [ADR-0010][0010-stable-entity-identity.md])?

## Decision Drivers

- One representation:
  a second IR for the SSA form buys nothing but conversions,
  and every pass, verifier, dump, and back end has to be written twice.
- Block parameters as the SSA mechanism:
  a value that is born at a join is a parameter of the join block,
  and a jump passes the arguments;
  this is what Cranelift and Waffle do,
  and it needs no separate phi nodes.
- Backend independence:
  no registers, no locals of a target, no instructions of a target.
- Totality over real input:
  a body that did not check is simply not lowered,
  and the pass itself reports nothing;
  what it cannot lower is a gap of the check, and a compiler bug the pass is loud about.
- Determinism:
  arenas and block order, never hash-map order ([ADR-0009][0009-pass-contract.md]).
- Source fidelity:
  every statement and terminator carries a span,
  because diagnostics and DWARF are built from them
  ([ADR-0020][0020-wasm-backend.md]).
- Snapshot testability:
  a dump of a body is a value a test compares ([ADR-0006][0006-snapshot-testing.md]).

## Considered Options

- **No MIR** — lower the checked HIR straight into a back end.
- **Typed MIR** — rustc-style: every local and temporary has a machine type,
  and the SSA form is a second pass over differently-shaped data.
- **CFG and SSA as two IRs** — a mutable-locals CFG IR,
  and a separate block-parameter SSA IR.
- **A uniform word CFG whose SSA form is the same shape** — one set of types,
  with the two forms told apart by their invariants and by the pass that last touched them.

## Decision Outcome

Chosen option: "A uniform word CFG whose SSA form is the same shape",
because the CFG form is only an intermediate between HIR and SSA,
and giving it a second representation would tax every consumer
for the duration of one pass.

The decision also answers [ADR-0005][0005-compiler-pipeline.md]'s open AIR question:
**there is no separate AIR stage.**
The lowering from the checked HIR goes directly to the CFG form;
the CFG form _is_ the normal form,
and the SSA construction is a pass over it.

"Typed and layout-resolved" in [ADR-0005][0005-compiler-pipeline.md]'s sense
is read here as a property of the **operators**, not of the values:
the checker's types are spent during lowering
into the choice of a `PrimOp` (`IntAdd` and not a generic `Add`) and of a callee,
and layout decisions appear when layouts exist
(a structure's fields choose a GC struct type, an `Int` chooses an immediate).
The values themselves stay uniform words,
which is what keeps the second back end from redesigning MIR.

### The crates

- `mlkc-mir` — the data structures, the verifier, and the dump.
  It depends on `mlkc-hir-def` (ids and entities) and `mlkc-span`, and on nothing above them.
- `mlkc-mir-build` — the lowering from HIR and the SSA construction.
  This is the pass crate, in the sense of [ADR-0009][0009-pass-contract.md].
- `mlkc-mir-opt` — the optimization passes, each a pure function over `Body`.

### A body

```rust
// mlkc-mir
pub struct Body {
    /// The entity whose body this is.
    /// A function declared inside a body has `local` set.
    pub owner: BodyEntityLoc,
    pub local: Option<LocalFunctionId>,
    /// The values the body is entered with: one per parameter of the owner, in order.
    ///
    /// A parameter is a value and not a slot: the first statements of the entry block
    /// bind the parameter slots to them, and both forms keep the list where it is.
    pub params: Vec<ValueId>,
    /// The block a function body enters.
    pub entry: BlockId,
    pub blocks: Arena<Block>,
    /// Definitions of SSA values.
    pub values: Arena<ValueData>,
    /// Slots of the CFG form; empty once the SSA pass has run.
    pub locals: Arena<LocalData>,
}

pub struct Block {
    /// The block parameters: where a value coming from several predecessors is born.
    pub params: Vec<ValueId>,
    pub stmts: Vec<Stmt>,
    pub term: Terminator,
}
```

A block is entered through its parameters and ends in exactly one terminator;
there are no fall-throughs and no implicit join points.

`ValueData` and `LocalData` carry what a dump, a verifier, and a debugger need,
and nothing a pass computes:
the span of a definition,
the name a slot was bound under,
and the source type the checker gave it.
They are what makes a word's origin recoverable after the uniform representation
([ADR-0018][0018-values-as-words.md]) threw the source type away.

### Places and operands

```rust
pub enum Place {
    /// A slot of the CFG form; it may be assigned many times.
    Local(LocalId),
    /// An SSA value; it is defined exactly once, by its statement or as a block parameter.
    Value(ValueId),
}

pub enum Operand {
    Value(ValueId),
    /// A read of a slot; only in the CFG form.
    Local(LocalId),
    Const(Const),
}
```

`Place` and `Operand` are the whole of the uniformity:
the same statement kind defines a slot in the CFG form
and a value in the SSA form,
and the same operand kind reads either.
A body is in one form or the other,
and the form is an invariant a verifier checks, not a type parameter.

### Statements

```rust
pub struct Stmt {
    pub kind: StmtKind,
    pub span: Span,
}

pub enum StmtKind {
    /// `place = rvalue`.
    Assign { place: Place, rvalue: Rvalue },
}

pub enum Rvalue {
    /// A copy of an operand.
    Use(Operand),
    Const(Const),
    Call { callee: Callee, args: Vec<Operand> },
    /// A word-level primitive; the operator says which.
    Prim { op: PrimOp, args: Vec<Operand> },
}

pub enum Callee {
    /// A function of the project, in this module or in another.
    Entity(EntityLoc<FunctionLoc>),
    /// A function declared inside the enclosing body.
    Local(LocalFunctionId),
    /// Later, when functions become values: a closure held in an operand.
    Indirect(Operand),
}
```

The first implementation has exactly one statement kind.
Later statements — a field write, an effectful call — are new variants,
not a redesign.

There is no notion of memory in MIR:
no pointers, no addresses, no load/store of a linear memory.
The WASM GC heap is the only heap,
and its objects are reached through structures and strings, not through addresses.
A native back end that uses a linear heap for its own reasons
is free to, under the same MIR.

### Constants and primitives

```rust
pub enum Const {
    /// A signed 31-bit integer; the range invariant of [ADR-0018][0018-values-as-words.md].
    Int(i32),
    Bool(bool),
    Unit,
    Str(Interned<str>),
}

pub enum PrimOp {
    IntAdd, IntSub, IntMul, IntDiv, IntNeg,
    IntEq, IntNe, IntLt, IntLe, IntGt, IntGe,
    BoolAnd, BoolOr, BoolNot, BoolEq, BoolNe,
    /// Identity of two references.
    RefEq,
}
```

An operator names its semantics, not an instruction:
`IntAdd` is the addition of two immediates with the wrapping of
[ADR-0018][0018-values-as-words.md],
`IntDiv` traps on a zero divisor and wraps the one whole case that leaves the range,
and a back end lowers each operator to its own encoding.
The untyped-ness of the operands is not lost information:
the MIR lowering picked the operator from the type the checker gave the operands,
so `+` on two `Int`s is `IntAdd` and `==` on two `Bool`s is `BoolEq`
([ADR-0017][0017-resolved-types.md], [ADR-0018][0018-values-as-words.md]).

### Terminators

```rust
pub enum Terminator {
    Goto { target: BlockTarget, span: Span },
    Branch {
        cond: Operand,
        then_: BlockTarget,
        else_: BlockTarget,
        span: Span,
    },
    Switch {
        scrutinee: Operand,
        arms: Vec<(Const, BlockTarget)>,
        otherwise: BlockTarget,
        span: Span,
    },
    Return { value: Operand, span: Span },
    /// Control that is not meant to be reached.
    Unreachable { span: Span },
}

pub struct BlockTarget {
    pub block: BlockId,
    pub args: Vec<Operand>,
}
```

`Branch` and `Switch` exist before the HIR can produce them:
the language has no `if`, no `match`, and no loops yet,
so today's lowering emits one block and a `Return`.
They are here because the first control-flow form of the language
must not be the moment MIR is redesigned;
the SSA construction is exercised on hand-built bodies until then.

### The two forms

|                | CFG form                                             | SSA form                                 |
| -------------- | ---------------------------------------------------- | ---------------------------------------- |
| produced by    | `mlkc-mir-build::lower_body`                         | `mlkc-mir-build::construct_ssa`          |
| `locals`       | may hold slots, assigned any number of times         | empty                                    |
| block `params` | empty                                                | one per value born at a join             |
| jumps          | pass no arguments                                    | pass one argument per parameter          |
| `Place`        | `Local` or `Value`                                   | `Value` only                             |
| `Operand`      | `Value`, `Local`, or `Const`                         | `Value` or `Const`                       |
| invariant      | every read follows an assignment on every path to it | every use is dominated by its definition |

The parameters of the _body_ are not in the table: `Body::params` holds one value per
parameter of the owner in both forms, a parameter is a value and not a slot,
and the construction neither moves the list nor makes parameters of them.
What the SSA form adds is the parameters of a _join_.

The verifier of `mlkc-mir` checks the invariant of the form it is asked about.
`Body::validate_cfg()` and `Body::validate_ssa()` share what is common
(edges match terminators, targets exist, arguments match parameters, arenas are ordered);
the difference is the table above.
The SSA verifier is the one the optimizers and the back ends rely on.

Uniformity is deliberate and has a price:
a body in the SSA form still carries an empty `locals` arena,
and the `Place::Local` variant exists in a type that cannot meet it.
The price is one `match` arm, paid once;
the benefit is that the dump, the verifier, the cost model,
and every optimization are written once.

### Lowering, from HIR to MIR

```rust
// mlkc-mir-build
pub fn lower_body(
    owner: BodyEntityLoc,
    tree: &ItemTree,
    body: &mlkc_hir_def::Body,
    source_map: &BodySourceMap,
    checked: &CheckedBody,
    resolution: &Resolution,
    deps: &CheckDeps,
) -> Body;
```

`Body`, the result, is `mlkc_mir::Body`:
the structure of this pass, named shortly.
The HIR's body is the one name that carries its crate,
because two `Body`s meet in this one signature;
the other inputs have no namesake and are named as they are.
They live where the stage that produced them left them
(`CheckedBody` and `CheckDeps` in `mlkc-hir-ty` and `mlkc-typeck`,
`Resolution` in `mlkc-resolve`, `BodySourceMap` in `mlkc-lower`),
and the driver assembles them ([ADR-0009][0009-pass-contract.md]);
when the temporary checker is replaced, `CheckDeps` changes its insides
and this signature does not change meaning.

Two of the inputs are the ones a first sketch of this record did not name.
The source map is where the nodes of the HIR body are written:
MIR carries a span for every definition, statement, and terminator,
and the lowering is the stage that copies them.
`Resolution` and `CheckDeps` are what the check read,
and they are what resolves the path of a call:
the lowering resolves it with `Walk::entity_of`,
the function the check resolves it with ([ADR-0016][0016-inter-module-resolution.md]),
so a callee is the entity the check called, and not a walk of a module table here.
`CheckDeps` is also what the lowering reads the classes of `Int` and `Bool` from.

- **Post-order, one temporary per compound expression.**
  Every expression is lowered into a slot of its own:
  the operands of an expression are read from the slots of its children,
  and the result is assigned to the expression's slot.
  A `let` binds the slot of its pattern for the scope of its body;
  a parameter is a value of `Body::params`,
  bound to a slot of its own by the first statement of the entry block.
  The CFG form is therefore a `let`-normal form already,
  and the SSA construction has work to do, which is the point.
- **Callees come from the HIR.**
  A path in a body is anchored to an entity, an import, a local, or a binding;
  the lowering reads the anchor and answers it with `Walk::entity_of`,
  and never walks a module table itself.
- **Operators come from the checked types.**
  A binary or unary expression is lowered by asking `CheckedBody` for the type of
  its operands and `Builtins` for which type class `Int` and `Bool` are.
  The first implementation knows the operators of the table above;
  a call of a user function is always `Callee::Entity` or `Callee::Local`.
- **Only checked bodies are lowered, and the lowering reports nothing.**
  A body whose check reported a mistake has no MIR:
  the driver asks for it only when the parser, the lowering of the HIR,
  and the check reported nothing about the file and the body,
  and codegen therefore never meets an expression whose meaning is a mistake.
  Semantics is checked in one place:
  what the checker accepts, the lowering lowers,
  and a construct the lowering cannot handle is a gap of the check,
  which the compiler answers with an internal exception and not with a diagnostic.
  The pass is therefore total over the bodies it is given:
  a body it stops on is a body no check should have accepted.

### SSA construction

```rust
pub fn construct_ssa(body: &Body) -> Body;
```

The pass is the on-the-fly construction of Braun et al.,
with block parameters in place of phi nodes:

1. walk the blocks in reverse postorder;
2. keep the current definition of every local per block,
   and when a read finds none, resolve it through the predecessors:
   a block with one predecessor reads from it,
   a block with several gets a block parameter of its own;
3. a parameter whose arguments all turn out to be one value is removed,
   and its uses are replaced by that value
   (Braun's trivial-parameter elimination) —
   this is where the copies the construction made disappear;
4. the parameters of the body (`Body::params`) are values and not slots:
   the construction neither moves them nor creates parameters for them,
   and the statements that bind them are rewritten like every other statement.

Because the whole CFG exists before the pass runs,
every block's predecessors are known,
and the sealing bookkeeping the algorithm needs
while a CFG is still being built is not needed here.

The classic placement of Cytron et al. — dominator tree, dominance frontiers,
then a renaming walk — computes the same SSA;
why it was not chosen is in the options below.

The result satisfies the SSA invariant of the table above.
What the pass does not do is cleanup:
empty blocks it leaves behind are removed by `simplify-cfg`
in `mlkc-mir-opt`, which runs as the first optimization.

### The pass pipeline

Per body, in this order, each stage a pure function the driver keys and memoizes
([ADR-0008][0008-compiler-driver.md], [ADR-0009][0009-pass-contract.md]):

1. `mir` — `lower_body`, the CFG form, for a body that checks clean;
2. `mir-ssa` — `construct_ssa`, the SSA form;
3. `mir-opt` — zero or more optimization passes;
4. `codegen` — one WASM function per body that has MIR ([ADR-0020][0020-wasm-backend.md]).

The optimization passes of `mlkc-mir-opt` are `Body -> Body` functions,
run in the order the driver names, each verifiable:

- `simplify-cfg` — remove unreachable blocks,
  merge a block into its single successor when the successor has one predecessor;
- `const-fold` — evaluate `Prim`s of constants with the semantics of
  [ADR-0018][0018-values-as-words.md];
- `copy-prop` and `gvn` — global value numbering over the word-level operators;
- `dce` — remove definitions no reachable terminator uses;
- later, `inline` — a whole-module or whole-program pass
  (the Thin-LTO of [ADR-0005][0005-compiler-pipeline.md]),
  planned for release builds,
  because it needs a call graph, which a body does not have.

Two rules bind every pass:

- **the SSA invariant survives it**: after a pass, `validate_ssa` holds,
  or the pass is a bug;
- **spans survive it**: folding or replacing a statement keeps the span of
  the statement it replaces, and dropping a statement drops its span.
  A debugger's line is a property of MIR, and optimizations may not lose it.

### What MIR does not decide

- **Layouts.** Fields, variants, and the shape of a structure are not designed yet
  ([ADR-0017][0017-resolved-types.md]);
  when they are, they become constants in the structure's `EntityLoc` and new `Rvalue`s,
  not new kinds of value.
- **Monomorphization and `impl` dispatch.**
  A call whose callee is generic needs a dictionary or an instantiation;
  the language declares no generics yet,
  so the check accepts no such call for the lowering to meet.
- **Closures.** `Callee::Indirect` is reserved for them.
- **Floats, exceptions, and effects.**
  Each adds constants, operators, or terminators.

### Positive Consequences

- One representation for both forms:
  the dump, the verifier, the analyses, and both back ends read one crate.
- The SSA form is reached by a pass,
  so a body edit invalidates the MIR of that body and of nothing else
  ([ADR-0004][0004-module-system.md]).
- Every optimization is a function over a value,
  testable by snapshotting the dump of its input and its output
  ([ADR-0006][0006-snapshot-testing.md]).
- The operators are the only place where the tagging of [ADR-0018][0018-values-as-words.md]
  is visible to optimizations,
  so an optimization written once works for every back end.
- A body that does not check produces no MIR,
  so no stage after the checker ever meets an expression whose meaning is a mistake.

### Negative Consequences

- The CFG form and the SSA form are told apart by invariants, not by types;
  a pass that is handed the wrong form finds out from `validate_ssa`,
  not from the compiler.
- Uniformity means a `Place` and an `Operand` carry a variant
  that only one of the two forms uses.
- A word has no type, so a back end that wants to avoid casts
  must reconstruct a refinement;
  that reconstruction is a pass of its own ([ADR-0020][0020-wasm-backend.md]).
- The lowering is `let`-normal per expression,
  which makes pre-SSA dumps verbose;
  the dumps are snapshots, so verbosity is visible but not free.

## Pros and Cons of the Options

### No MIR

The checked HIR is lowered directly into a back end.

- Good, because it is the shortest path to a running program.
- Bad, because every optimization becomes a back-end pass,
  and the second back end gets none of them.
- Bad, because the HIR is a tree and the target wants a CFG,
  so the structurization of control flow is entangled with expression lowering.

### Typed MIR

Every local and temporary has a machine type, as in rustc's MIR.

- Good, because a back end reads types directly, and scalars are unboxed.
- Bad, because the machine type of a `Param` is not known,
  so the representation decision moves out of [ADR-0018][0018-values-as-words.md]
  and into the checker.
- Bad, because it duplicates what the checker already decided,
  and the duplication must be kept in step with `Ty`.

### CFG and SSA as two IRs

A mutable-locals CFG IR, and a separate block-parameter SSA IR.

- Good, because each IR carries only the invariants it needs,
  and a misuse is a type error.
- Good, because the lowering is unconstrained by the SSA invariants.
- Bad, because every pass, dump, verifier, and back end is written twice,
  and the conversion between the two is a place for bugs with no semantics.
- Bad, because the SSA IR and the CFG IR evolve together,
  and a change to one is a change to both.

### A uniform word CFG

One set of types; the forms differ in their invariants.

- Good, because a pass is written once and works on either form,
  as long as it respects the invariants it declares.
- Good, because the SSA construction and the optimizations share one dump
  and one verifier.
- Good, because the representation of a value is uniform
  ([ADR-0018][0018-values-as-words.md]),
  so MIR has no reason to grow two shapes.
- Bad, because invariants that a type could carry are carried by convention and checks.

### The SSA algorithm: on-the-fly construction

Braun et al.'s construction, chosen:

- Good, because one walk in reverse postorder builds the form;
  no dominator tree and no dominance frontiers are computed.
- Good, because a parameter that turns out to carry one value
  is removed by the same walk, not by a later cleanup.
- Good, because it matches the shape of the pass we have:
  the CFG is complete before the pass runs,
  and the sealing machinery of an incremental frontend is not needed.
- Bad, because the construction can create parameters
  a minimal placement would not have created,
  and both the removal and `simplify-cfg` exist to clean them up.

Cytron et al.'s placement, not chosen:

- Good, because it is the classic formulation,
  and it places the minimal set of parameters before any cleanup.
- Bad, because it needs dominators and frontiers as separate analyses,
  and a second walk to rename — more machinery for the same SSA.
